# 资料库卡片图片性能检查

## 原因与边界

原先卡片直接使用 cover_url，CSS 将图片裁到 150px 高，但网络仍下载原始图片。读取 API 返回 `Cache-Control: private, no-store`，没有 ETag；每次都进行图片归属查询、Lstat、完整文件读取和 SHA-256 校验。服务端 GET 不解码原图，浏览器仍要解码全部像素。生产会话另有 session/user 两次查询，属于现有认证，保留。

卡片已有 lazy loading、稳定 ID key。onMounted 与非 immediate 的路由 watch 不重复初始化；同专题加载时不销毁目录。新增 Chromium 回归确认：单一卡片目录只请求一次小图，不下载原图。打开阅读区仍会请求原图，这是正常的大图阅读；未采集用户当前浏览器的实际网络日志，不将数据库内重复上传误判为网络重复请求。

本地正式数据库只读检查发现 5 条上传记录，其中 4 条是相同字节；实际已保存本地页面封面只有一条。以下使用两种现有上传文件的临时副本作相同图片的前后对比，不声称当前两张画面一定对应两个不同文件。图片内容、原标题、来源、登录凭据均未写入仓库。

## 实现

卡片的显示地址为 `/api/v1/library/images/<ID>?variant=card-v1`，只有这一个固定小图规格，不开放任意尺寸。最长边 640px，不放大小图、保持比例，JPEG quality=80；透明 PNG 仅小图合成白底。复用标准库 JPEG 编码和现有 x/image 缩放依赖。现有 WebP 依赖只有解码，首版不为 WebP 编码新增 C 库或服务。原始 PNG/JPEG/WebP 不转换。

生成结果存于数据库同级 `uploads/library/thumbnails/card-v1/<ID>-<原图SHA256>.jpg`，沿用 Docker `/app/data` 挂载。历史记录首次访问也可生成。单实例使用可取消的生成信号量、等待后复查缓存、临时文件原子替换，避免并发重复生成；单次解码有原始大小/像素上限。热缓存不解码、不读取或哈希原图。缓存单文件上限 512KiB，总预算最多 256MiB 或原图配额的四分之一，超出按生成时间逐出小图，绝不删除原图。显式清理未引用原图时同时清理对应小图。

首次生成在该图片请求内执行，会增加一次解码成本，其他图片的热缓存及原图请求不等待生成信号量；没有新增后台服务或无界 goroutine。上传/备份/清理仍沿用现有文件锁；首次生成期间文件变更需等待该次读锁。

原图和小图响应均设置 `private, no-cache`、ETag、`Vary: Cookie, Authorization`、nosniff、同源 CORP/CSP。no-cache 允许私有存储，但必须每次重新认证/校验，避免注销后直接使用未校验的缓存。先查图片归属和原文件存在/大小，再处理 If-None-Match（含弱标签、标签列表、*）；匹配时 304，不读取任何图片正文。未登录仍 401，不能通过 ETag 绕过认证；不公开目录、不在 URL 放 Token。

存储的 cover_url、Markdown 及原图 ID 不变，无迁移。阅读/正文、专题导出和完整备份继续使用原图并校验原图哈希。小图是可再生成缓存，不进入 ZIP 正式备份/导出；原图恢复后再次访问即可生成。真实临时 SQLite + ZIP 恢复测试覆盖这一路径。

## 同图测量（2026-10-12，本机隔离 HTTP）

通过 `httptest.NewServer`、真实 Go HTTP 客户端、生产 SessionAuth、临时用户/会话/SQLite 和相同图片副本测量；没有修改正式数据库。下表大小为 HTTP 图片正文，耗时包含本机请求、认证、文件读取及传输，不包含云服务器公网带宽或浏览器完整解码/绘制。

| 样本 | 原图尺寸/字节 | 优化前单次 GET | 小图尺寸/字节 | 首次生成 GET | 小图已生成 GET | 条件 GET |
| --- | --- | --- | --- | --- | --- | --- |
| A | 3840×2160 / 6,762,946 | 20.5–23.3ms | 640×360 / 76,145 | 542–624ms | 0.69–0.87ms | 304 / 0字节 / 0.49–0.53ms |
| B | 4032×3024 / 1,964,529 | 6.6–7.4ms | 640×480 / 68,985 | 175–180ms | 0.89–1.07ms | 304 / 0字节 / 0.43–0.54ms |

合计图片正文从 8,727,475 字节减少到 145,130 字节（约 **98.3%**）。两张不同图片一次加载仍是 2 个图片 GET；再次校验仍为 2 个请求，但从两个 200/全量传输变为两个 304/无图片正文，不宣称请求数为零。原图 200 MIME=image/jpeg，原响应头 private,no-store/nosniff/CORP=same-origin/CSP=default-src 'none'; sandbox/Content-Disposition=inline、无 ETag；优化后小图为 image/jpeg，private,no-cache、ETag 和 Vary，其他安全头保留。200 响应 Content-Length 与上述字节大小相同，未使用 chunked；304 不携带图片正文。

首次生成比本机读取原图慢，这是一次性的 CPU 成本；公网带宽收益未在云服务器实测。样本 EXIF orientation=1。小图另保留 JPEG 的最小方向标记，避免手机照片方向变化，不复制 GPS/相机等其他 EXIF；原图保留全部元数据。

复测入口：将私有样本保存在仓库外 sample-0/sample-1，设置 LIFEOS_IMAGE_PERF_DIR 后运行 `go test ./internal/httpapi -run '^TestLibraryImagePerformance$' -v -count=1`。常规测试不读取真实图片，该测量默认跳过。

## 验证

- Go 全量测试、go vet、服务构建通过；新增小图专项测试覆盖 PNG/JPEG/WebP 历史输入、比例、并发复用、取消、损坏缓存重建、JPEG 方向标记 2–8、私有归属、无效规格、磁盘预算与清理。
- 原图专题导出、封面共享引用、完整 ZIP 备份和恢复后再生成通过。
- 前端 typecheck、35 项单元测试、生产构建通过；Vite 现有大包提示仍在。
- 资料库/图片 Playwright 18 项通过，含实际卡片请求计数、正文/阅读封面仍使用原图、上传/粘贴/拖放、失败反馈、刷新、390px/1440px 与安全渲染。
- 正式本地容器未重新部署；未执行云服务器带宽和用户真实浏览器解码耗时测量。
